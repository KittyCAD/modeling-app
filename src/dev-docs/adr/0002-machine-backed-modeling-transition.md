# Reuse modelingMachine while moving Modeling into editor views

Moving the file route's execution and scene ownership into independent editor views is already a substantial architecture change. Use a view-owned instance of `modelingMachine`, its sketch child actors, and the existing toolbar and dialogs for the initial transition. Preserve their interaction flows through explicit document, history, native-runtime, settings, and picking adapters, so colleagues can review ownership changes without also reviewing replacement CAD algorithms.

The editor remains the authority for source text, undo history, and persistence. Each Modeling view owns its connection, native model, manager, and actors. The machine borrows those resources; it does not acquire a global editor, singleton connection, second save owner, or competing scene-input controller. An external edit or execution-setting change retires that owner before executing a replacement model.

Independent tool and interaction contributions remain the intended direction. The earlier Circle/move controllers, contributed command definitions, dialog modes, and sketch-session prototype demonstrated that direction; they are deferred from the initial migration rather than rejected. Introduce them incrementally after the editor ownership transition, with one authoritative interaction implementation at a time. Extract an existing behavior behind explicit dependencies, adapt the legacy machine to it, and exercise both consumers before replacing a machine flow. A contribution must not start a second native editing session alongside the active machine child.

The existing selection and presentation boundaries provide migration seams. A sketch interaction changes the activity within a Modeling editor mode; it does not create another document or editor presentation mode. The initial interaction-session facade projects machine state for view extensions. Later contributions can replace individual flows without requiring an all-at-once removal of XState or making actor internals the public extension API.

This refines the proof-of-concept scope in [ADR 0001](0001-app-owned-scene-host.md): the initial consumer reuses the broader legacy tool system instead of individually porting every tool. Reuse makes those tools reachable but does not establish tested parity for every operation, renderer, or project-dependent feature. Live renderer checks and the remaining project/export and feature-tree adapters remain explicit follow-up work.

## What this stack establishes, and what it does not

The migration establishes ownership boundaries. It does not finish the replacement architecture. In particular:

- `machine/host.ts` still constructs `KclManager` and the modeling actor directly. View-bound command definitions register through the shared application command service; its single command actor captures the target modeling actor when a command opens. The KCL registry factory selects this host; alternative hosts are not registry contributions yet.
- `ModelingViewContext` on the primary branch still exposes the full executor, session, and interaction controller. These are wider capabilities than extensions should ultimately receive. The optional selection-bridge branch narrows parts of that surface; the primary branch alone does not enforce the final boundary.
- `modelingInteractionsFacet` and `modelingInteractionViewsFacet` exist, but the machine host's `enter` adapter only handles Start Sketch. Registering an arbitrary interaction does not currently replace its machine flow. Interaction views and status items are working contribution points; general interaction replacement remains work.
- The optional `modelingToolsValueSpec` contributes argument editors. Its Extrude/Loft adapters still submit through the machine's commands. This is not yet a registry of independent modeling-operation implementations.
- Shared React views have explicit hosts, but some still read machine snapshots and invoke manager methods. Extracting a view does not by itself make its behavioral dependencies replaceable.

The decision accepts these temporary dependencies to reduce simultaneous behavior changes. It does not make their types or events the permanent extension protocol. New contributions should not acquire additional manager or actor authority to work around a missing capability: add the narrow capability at the owning service and adapt the legacy consumer to it.

## Replacement sequence

Replace responsibilities in vertical slices rather than introducing a second object with all of `KclManager`'s methods. Each row names the existing seam and the evidence needed before the legacy responsibility can be removed. These are planned steps, not capabilities claimed to be complete on this branch.

| Responsibility today | Replacement and registry composition | Removal criterion |
| --- | --- | --- |
| `KclManager` owns an editing surface, native checkpoint listeners, and document mutations | Keep the editors service as source/history authority and the save capability as persistence owner. Express accepted tool edits as editor transactions. Keep native checkpoint interpretation in an execution-owned history adapter; its retained history data must not own a view, manager, actor, or native context. | Existing text and native-preview history works across two views and after the originating native owner closes. New operations do not need `manager.editorView` or `manager.writeToFile`. The hidden CodeMirror surface can then be removed from the new view's execution path. |
| `KclManager` parses, executes, publishes diagnostics, and holds AST/artifact state | Publish execution snapshots and explicit operations through the executor/runtime services. Keep source capture in the project/document layer and native calls in the runtime's existing queue. First let the manager delegate to those services, then let migrated tools consume those same capabilities directly. | Parsing, evaluation, execution, and error recovery have one authority. A migrated operation can read a completed execution and commit its edit without constructing a manager or accidentally triggering a second execution. |
| `modelingMachine` coordinates entering, editing, and leaving sketches | Contribute interaction definitions through the registry and let the view acquire the chosen interaction with explicit execution, input, and cleanup capabilities. Generalize dispatch beyond the current Start Sketch ID. A legacy activity adapter can supply the existing machine flow until a particular activity has migrated. | The same interaction-host contract can acquire either the legacy adapter or one independent activity. Acquiring the latter must not also enter a legacy sketch child or acquire a second native editing lease. Withdrawal, cancellation, and external execution release the active activity before another owner starts. |
| Machine child actors implement sketch tools and multi-step gestures | Extract one complete existing interaction behind explicit scene input, snapping, native-operation, preview, and commit dependencies. Contribute its definition and availability through the registry; contribute its keybinding beside it using the existing scoped keymap system. Preserve explicit phases and cancellation even when the representation no longer needs XState. | Both the legacy adapter and independent consumer exercise the shared behavior. Circle, move, and later tools retain modifier handling, snapping, hover/selection, repeated operations, Escape, pending-preview ordering, tool switching, units, and cleanup before their actor-specific flow is retired. |
| Machine command tables and toolbar configuration determine operations and availability | Evolve tool contributions from dialog factories into operation definitions with argument policy, availability, execution requirements, and a handler. The toolbar and dialogs consume those definitions. A machine-backed handler is one adapter, rather than the public command format. | An added operation can contribute its definition and scoped keybinding without another dispatch branch or a new machine state. Removing the contribution removes its command and presentation. Its handler remains bound to the invoking view's execution. |
| Machine context and engine subscriptions carry selection, picking, and source mapping | Expose owner-qualified read/clear and picking capabilities. Keep ordinary view selection, dialog picking, and native sketch selection distinct. Registry-composed selection bridges interpret cross-view correspondence; renderers consume visual styling rather than source-selection semantics. | A status item or linked view can consume selection without inspecting actor states. Stale execution targets and ambiguous source mappings cannot silently populate an argument. An independent tool can borrow input without changing another scope's selection or leaving legacy input active. |
| `SceneEntities`, `SceneInfra`, and React components mix scene behavior with presentation | Reuse the existing geometry and interaction implementations behind explicit scene/presentation hosts. Keep renderer resources and input controllers owned by the view/activity lifetime. React subscribes and renders controls, attaches DOM, and handles local focus; native scheduling, gesture phases, and document publication belong in library services/controllers. | Remounting a React view does not restart an operation, allocate another native model, or lose its activity. Both rendering presentations exercise the same interaction contract. Presentation teardown releases only resources it owns. |
| Legacy project metadata and route context supply files, export, and feature-tree behavior | Resolve documents and project sources through the project services and save capability. Add explicit export metadata and feature-tree selection/query adapters at their registry boundaries instead of fabricating a legacy `Project` or passing `ZdsProject` into new tools. | A new view can execute, save, export, and accept feature-tree picks without depending on the file route or its project controller. The remaining export and feature-tree TODOs are completed before claiming parity for those features. |

`ConnectionManager` is not a target for wholesale replacement in this decision. Per-view connection ownership and the presentation host remain useful with either interaction implementation. The future zoo-web-view presentation adapter described in ADR 0001 is separate from replacing modeling actors and managers.

## How to review whether the route remains open

Review the primary stack for dependency direction, not just for the presence of adapters. The compatibility code should depend on editor/execution/scene capabilities; those capabilities must not require a manager or actor to exist. In particular:

1. Trace a source edit from `machine/document.ts` into the editor, and a native operation through `runtime.borrowModel` and the existing queue. Confirm that save ownership, imported-source policy, and native disposal do not move back into the manager.
2. Inspect `registry/contract.ts` separately from `machine/host.ts` and `machine/View.tsx`. Distinguish published contribution capabilities from host-only ownership. Any new public `KclManager`, actor reference, XState snapshot, machine event union, or hidden editor access is a retirement cost that should be justified or replaced with a narrower operation.
3. Check that shared toolbar, dialog, and Three.js extractions preserve existing control flow. New behavioral changes should be explicit, separately testable slices. This prevents a migration from becoming a rewrite concealed by an adapter name.
4. For the first independent interaction, require a composition test in which the view uses that contribution without acquiring the legacy host. A second configuration should exercise the legacy adapter against the same host contract. The current stack's native host tests establish isolation and lifetime behavior; they do not yet prove this alternate composition.
5. Require execution-qualified input and history tests at each replacement: two views of one document, source/import/settings refresh, pending native work, cancellation, view closure, and undo/redo after closure. Selection, correspondence, status, and presentation contributions should survive changing the interaction implementation.

The concrete next architecture step is therefore a registry-composed interaction host with a legacy activity adapter, plus one independent activity demonstrating the alternate composition. It is not another collection of forwarding methods on `KclManager`, nor deleting the whole machine at once. The preserved prototype is evidence for individual slices and a source of reusable controllers, not proof that all legacy behavior has already been replaced.

`KclManager` can leave the new editor path after its document, execution-state, query, and interaction responsibilities have moved to these services. `modelingMachine` can leave that path after its remaining activities and handlers have registry-composed replacements. The legacy file route may continue using either while it still exists. Removing XState everywhere, or removing all state from multi-step interactions, is not a prerequisite for either milestone.
